# lifecycle_probe — что реально прилетает вокруг диалога пермишена

Замер для [rust-mobile/android-activity#174](https://github.com/rust-mobile/android-activity/issues/174).

## Зачем

Под `NativeActivity` колбэка `onRequestPermissionsResult()` не существует. Предложенный
воркэраунд — считать сигналом «диалог закрылся» то, что активити **резюмится**. Это
допущение никем не измерено: диалог пермишена — translucent-активити **чужого процесса**,
и она вполне может лишь забирать фокус, не паузя нашу. Плюс OEM-сборки любят расходиться.

Проба отвечает на это фактом, а не рассуждением.

## Почему отдельный крейт, а не флаг в приложении

`eframe` забирает event loop себе — `MainEvent` до прикладного кода не доходит, изнутри
`fretboard` переходы **невидимы**. Поэтому проба на голом `android-activity`, без eframe,
и со своим `[workspace]`: папку можно скопировать наружу и собрать где угодно.

JNI-обвязка намеренно продублирована из `src/android_perm.rs`, а не расшарена — чтобы
проба оставалась самодостаточной.

## Сборка и запуск

```sh
cd probes/lifecycle_probe
ANDROID_NDK_ROOT=/opt/android-sdk/android-ndk-r27c ANDROID_HOME=/opt/android-sdk \
    cargo apk run --lib
```

Пакет `com.fretboard.lifecycleprobe` — **отдельный** от `com.fretboard.snail`, ставится
рядом и на пермишены основного приложения не влияет.

Смотреть лог:

```sh
adb logcat -s probe
```

### Обязательное предусловие

Пермишен должен быть **НЕ выдан** — иначе диалог не покажется и мерить будет нечего.
Свежая установка это гарантирует. Для повторного прогона:

```sh
adb uninstall com.fretboard.lifecycleprobe
```

(`pm grant`/`revoke` на MIUI не работает — `SecurityException`, см. KICKOFF-док.)

### Как проходит прогон

1. Экран должен быть **разбужен физически** — eframe тут ни при чём, но MIUI режет
   `adb input keyevent`, а на спящем экране активити не резюмится.
2. Проба ждёт первый `Resume`, выдерживает 2 с (чтобы стартовый залп событий закончился)
   и показывает диалог — в логе он обрамлён маркерами `=== FIRING ... ===`.
3. **Нажать «Разрешить»** — и смотреть, что легло между маркером и строкой
   `>>> checkSelfPermission FLIPPED`.

Проба крутится вечно, глушится `adb shell am force-stop com.fretboard.lifecycleprobe`.

## Что мы измеряем — три исхода, все полезные

| В логе между `FIRING` и `FLIPPED` | Вывод для дизайна |
|---|---|
| `MainEvent::Pause` … `MainEvent::Resume` | воркэраунд на lifecycle рабочий |
| только `LostFocus`/`GainedFocus` | ловить надо **фокус**, не lifecycle |
| ничего, флип замечен только опросом | подход мёртв, поллинг незаменим |

Поэтому `MainEvent` печатается целиком через `Debug`, а не матчится по заранее выбранным
вариантам: если прилетит что-то, чего мы не ждали, оно попадёт в лог, а не потеряется.

Отдельно стоит заметить, **приходит ли `Resume` вообще без нажатия** — если юзер уводит
диалог в шторку/настройки. Ровно этот край и заставил [nusb#150](https://github.com/kevinmehall/nusb/pull/150)
завести `ActivityLifecycleCallbacks`: там диалог мог исчезнуть без интента.
